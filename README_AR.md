# تحديثات إدارة المحتوى

تمت إضافة نظام إدارة محتوى موسع مع الحفاظ على وظائف المنصة السابقة:

- التحكم في إتاحة الفيديو والصوت والألعاب والاختبارات والكتب/المذكرات لكل الطلاب أو لطلاب محددين.
- كارت مستقل للكتب والمذكرات في لوحة المعلم.
- رفع PDF والصور (PNG/JPG/WEBP) بنفس أسلوب الرفع الحالي مع شريط تقدم وإغلاق نافذة الحفظ فور بدء الرفع.
- تعديل بيانات الملفات، استبدال الملف نفسه، أو حذفه.
- عرض الملفات للطالب وولي الأمر وفق الصف وقاعدة الإتاحة المحددة من المعلم.
- التحقق من الصلاحيات على الخادم، وليس الواجهة فقط.
- استمرار حساب ولي الأمر الواحد المرتبط بعدة أبناء.

## تشغيل

```bash
npm install
npm start
```

للنشر على Render، يجب استخدام تخزين دائم (Persistent Disk أو خدمة تخزين ملفات خارجية) للمجلدات `data`, `videos`, `audios`, `games`, و`documents` حتى لا تضيع الملفات عند إعادة نشر الخدمة.


## نظام المواد المتعددة للصف
- الصف الواحد يمكن أن يحتوي على عدة مواد، ولا يتم إنشاء صف جديد عند إضافة مادة.
- لكل طالب قائمة مستقلة بالمواد المسموح بها داخل صفه: كل المواد، مادة واحدة، مجموعة مواد، أو حجب الجميع.
- الطالب يستخدم اسم مستخدم وكلمة مرور واحدين للوصول إلى جميع المواد المسموح بها.
- يمكن ربط الفيديو والصوت واللعبة والكتاب/المذكرة والاختبار بمادة محددة داخل الصف.
- تم إضافة تحقق على الخادم يمنع الطالب من فتح محتوى مادة غير مسموح بها حتى عبر رابط مباشر.

## حفظ البيانات على Render
المشروع يستخدم `/var/data` على Render لتخزين قاعدة البيانات والملفات المرفوعة، مع Persistent Disk بحجم 10GB في `render.yaml`. كما أصبحت قاعدة البيانات تُكتب بشكل ذري مع نسخة احتياطية `db.json.bak` لتقليل خطر فقدان البيانات بسبب انقطاع أثناء الكتابة.

**مهم:** إذا كانت خدمة Render الحالية منشأة يدوياً ولم يتم تطبيق `render.yaml` عليها، يجب ربط Persistent Disk للخدمة الحالية على `/var/data`. ربط GitHub وحده لا يجعل الملفات المحلية دائمة بعد إعادة التشغيل.

## إصلاح خطأ Render: EACCES عند `/var/data`

تم تعديل `server.js` بحيث لا يتوقف التطبيق أثناء الإقلاع إذا كان Render يمرر `DATA_DIR=/var/data` بينما الـ Persistent Disk غير مربوط فعليًا. التطبيق يختبر قابلية الكتابة أولًا، وإذا كان المسار غير قابل للكتابة ينتقل تلقائيًا إلى مسار بديل قابل للكتابة بدل ظهور `EACCES: permission denied, mkdir /var/data`.

**للتخزين الدائم بعد إعادة النشر:** يجب أن تكون خدمة Render على خطة تدعم Persistent Disk وأن يكون القرص `edu-data` مربوطًا على `/var/data`. ملف `render.yaml` الحالي ينشئ هذا الإعداد عند استخدامه كـ Blueprint. تم حذف متغيرات `DATA_DIR/GAMES_DIR/...` الإلزامية من `render.yaml` حتى لا تجبر الخدمة على `/var/data` إذا لم يكن القرص موجودًا. إذا كان القرص موجودًا، سيختاره التطبيق تلقائيًا.

إذا كانت الخدمة الحالية منشأة من Dashboard وليست Blueprint، أضف Persistent Disk من إعدادات الخدمة: **Disks → Add Disk → Mount Path: `/var/data`** ثم أعد النشر. لا تضع `DATA_DIR=/var/data` يدويًا بدون قرص دائم؛ سيبدأ التطبيق بفضل آلية fallback، لكن البيانات الموجودة في المسار البديل ليست تخزينًا دائمًا بعد إعادة إنشاء الخدمة.


## قاعدة البيانات الدائمة عبر Supabase

أضيف دعم مزامنة قاعدة بيانات المنصة إلى Supabase. عنوان المشروع يُبنى تلقائيًا من `SUPABASE_PROJECT_ID`.

### إعداد Supabase مرة واحدة
1. افتح Supabase SQL Editor.
2. شغّل الملف `supabase/schema.sql`.
3. في Render أضف `SUPABASE_PROJECT_ID` و`SUPABASE_PUBLISHABLE_KEY` و`SUPABASE_SECRET_KEY`.
4. قيمة `SUPABASE_SECRET_KEY` يجب أن تكون **Secret key** من Supabase (`sb_secret_...`) وليس الـ publishable key. لا تضعها في GitHub.

الـ publishable key وحده غير مناسب للوصول الموثوق إلى بيانات الطلاب من الخادم؛ لأن سياسات RLS لا يجب أن تفتح قاعدة البيانات للزوار. الكود يدعم المفتاحين، ويستخدم الـ Secret key للمزامنة الآمنة. إذا لم يتم توفير Secret key سيستمر التطبيق محليًا، لكنه سيطبع تحذيرًا واضحًا.

عند تشغيل المنصة لأول مرة بعد إنشاء الجدول: إذا لم توجد صف `main` في Supabase، يرفع التطبيق قاعدة البيانات المحلية الحالية إلى Supabase. إذا كانت صف `main` موجودة، يحملها التطبيق من Supabase ويستخدمها كمصدر البيانات الأساسي.


## تشغيل الفيديو والصوت وPDF والصور والألعاب من Telegram File ID
تمت إضافة مصدر جديد للمحتوى باسم **Telegram File ID** بدون إزالة أو تعطيل المصادر القديمة:

- الفيديو: رابط مباشر + رفع من الجهاز + Telegram File ID.
- الصوت: رابط مباشر + رفع من الجهاز + Telegram File ID.
- PDF والصور: رفع من الجهاز + Telegram File ID.
- الألعاب: رفع HTML من الجهاز + Telegram File ID لملف HTML.
- الاختبارات الإلكترونية: الاختبار نفسه يظل اختبارًا داخليًا كما هو، مع دعم صور الأسئلة والاختيارات وملاحظات المعلم من Telegram File ID، بالإضافة إلى الفيديو/الصوت المرتبطين بالملاحظة.

### إعداد Telegram على Render
أضف متغيرًا سريًا في Render:

```text
TELEGRAM_BOT_TOKEN=ضع_توكن_البوت_هنا
```

لا تضع Bot Token في GitHub أو في ملفات الواجهة. المتصفح لا يرى التوكن؛ الخادم فقط يتصل بـ Telegram Bot API ويعمل كـ proxy للملف مع التحقق من جلسة الطالب والصف والمادة والإتاحة.

### طريقة الاستخدام
في نموذج إضافة المحتوى اختر **Telegram File ID** ثم ضع قيمة `file_id` التي أعادها Telegram Bot API. بالنسبة للـ PDF والصور اختر نوع الملف الصحيح. بالنسبة للألعاب يجب أن يكون ملف HTML مناسبًا للتشغيل داخل iframe، ويفضل أن تكون اللعبة self-contained أو تستخدم مواردها من روابط HTTPS مطلقة.

### ملاحظة عن أحجام ملفات Telegram
حدود تنزيل ملفات Telegram عبر Bot API تختلف حسب واجهة/خطة Telegram المستخدمة؛ لذلك الملفات الكبيرة جدًا قد تحتاج تخزين ملفات مخصصًا أو CDN. النظام لا ينقل ملفات Telegram إلى قاعدة Supabase؛ يتم حفظ الـ File ID فقط في قاعدة البيانات، بينما الملف يبقى على Telegram.

### الحفاظ على المصادر القديمة
المحتوى الذي تم إدخاله سابقًا كرابط أو رفع مباشر يظل بنفس `sourceType` والروابط/الملفات الخاصة به. إضافة Telegram لا تستبدل ولا تحذف أي مسار قديم.


## دعم Google Drive وتشغيل الملفات داخل المنصة
تم تحسين مسار Google Drive ليعمل كـ proxy مؤمّن من الخادم بدل الاعتماد على رابط Drive الخام داخل عناصر الوسائط. هذا يعالج حالات الصفحة البيضاء وصفحة تأكيد Google التي تظهر أحياناً عند الملفات الكبيرة العامة.

يدعم النظام الآن:
- الفيديو: تشغيل مباشر داخل مشغل المنصة مع دعم طلبات Range/استكمال التشغيل.
- الصوت: تشغيل مباشر داخل مشغل المنصة.
- PDF والصور: عرض مباشر داخل نافذة المنصة.
- HTML/الألعاب: تشغيل ملف HTML داخل iframe معزول.
- الاختبارات والملفات الخارجية: فتحها داخل المنصة مع مسار Drive مستقل.
- روابط Drive الشائعة التي تحتوي على معرّف الملف، مثل `file/d/.../view` و`open?id=...`.
- معالجة تأكيد Google Drive للملفات الكبيرة العامة تلقائياً عند الحاجة.

**مهم:** يجب ضبط مشاركة الملف في Google Drive على **أي شخص لديه الرابط — مشاهد (Viewer)**. ولتقليل التنزيل، عطّل خيار التنزيل/النسخ/الطباعة في إعدادات المشاركة عندما يكون متاحاً.

## ألعاب HTML بالكود من المعلم
أصبح بإمكان المعلم من **الألعاب التعليمية → لعبة جديدة** اختيار **كتابة / لصق كود HTML** ثم إدخال HTML/CSS/JavaScript وتعديله لاحقاً. الكود لا يُرسل إلى واجهة الطالب في بيانات لوحة الطالب، وتعمل اللعبة داخل iframe معزول `sandbox` ومن دون `allow-downloads`.

كما بقيت الخيارات القديمة كما هي: رفع ملف HTML، Google Drive، وTelegram File ID.

**حد الحماية:** لا يمكن لأي تطبيق ويب منع أدوات المطور أو تصوير الشاشة أو نسخ ما يظهر على الشاشة منعاً مطلقاً. لذلك الحماية هنا تمنع التنزيل من واجهة المنصة وتمنع كشف الكود في واجهة الطالب، مع بقاء التحقق والصلاحيات على الخادم.

## إصلاح Google Drive للاختبارات
- مسار `drive-stream/test/:id` مستقل عن مسار المستندات.
- روابط Drive للاختبارات والملفات لا تعتمد على فتح صفحة Google Drive داخل الصفحة الرئيسية للمنصة.
- روابط `forms.gle` وGoogle Forms مدعومة كما كانت.

## تحديث تشغيل الاختبارات والألعاب التعليمية
- تمت إضافة دعم صريح لروابط Google Forms من نوع `forms.gle` و`docs.google.com/forms`، مع تحويلها إلى وضع التضمين `embedded=true` عبر الخادم لتجنب مشكلة الصفحة البيضاء الناتجة عن فتح الرابط المختصر مباشرة داخل iframe.
- تم الحفاظ على تشغيل ملفات Google Drive الأخرى عبر المسار المحمي داخل المنصة.
- يمكن للمعلم إنشاء لعبة تعليمية عن طريق لصق كود HTML/CSS/JavaScript كنص وتعديله لاحقاً من لوحة المعلم.
- كود اللعبة لا يُرسل ضمن بيانات الطالب، وتُشغّل اللعبة داخل iframe مع sandbox وبدون صلاحية `allow-downloads`.
- تم الإبقاء على الوظائف الأخرى والرفع والروابط والصلاحيات والتقارير كما هي.
